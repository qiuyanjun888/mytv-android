# 代码审查

## 概览

用发现缺陷的视角审查变更。相比样式反馈，优先关注正确性、行为回归、生命周期与线程问题、播放稳定性，以及缺失的测试。

在审查这个仓库时，加载 [references/android-tv-player-review.md](references/android-tv-player-review.md)，以确保审查覆盖电视导航、播放器行为和应用中的高风险集成点。

## 审查流程

### 建立上下文

- 先看 diff，再在风险较高时完整阅读被修改的文件。
- 在判断行为之前，沿着受影响的调用点、状态持有者和生命周期边界继续追踪。
- 检查该改动是否会对 Leanback、手机端或平板端流程产生不同影响。
- 先理解预期行为再看测试；只有在缺失覆盖会带来实际风险时，才把它作为问题提出。

### 查找问题

- 优先指出具体缺陷，而不是带有猜测性的清理建议。
- 优先关注崩溃风险、播放失效、生命周期泄漏、焦点或遥控器操作陷阱、安全回归，以及兜底行为失效。
- 将缺失测试视为次级问题，但当行为已变化且验证不足时，要明确指出。
- 忽略细微的风格差异，除非它们会掩盖缺陷、模糊意图或破坏现有约定。

### 验证问题

- 尽可能给出精确的文件路径和行号。
- 解释失败模式，而不只是指出代码味道。
- 当仅凭 diff 无法判断时，明确写出你的假设。
- 没有可信的运行时场景，就不要声称存在问题。

### 编写审查结论

- 先列出问题，并按严重程度排序。
- 仅在确有需要时再补充开放问题或假设。
- 只有在有价值时，才在问题之后附上一段简短的变更总结；否则可以省略。
- 如果没有发现问题，要明确说明，并补充剩余风险或测试缺口。

## 项目特定的优先关注点

- 检查 Leanback 焦点移动、方向键处理、长按行为和返回导航，因为 Compose 中的电视端回归很容易漏掉。
- 检查 Media3 播放器初始化、媒体源选择、重试逻辑、缓冲状态切换、渲染 surface 绑定和释放路径，因为播放相关改动常常只会在运行时暴露问题。
- 检查仓库、解析器、缓存和设置改动是否引入主线程阻塞、陈旧状态、错误的历史记录修改、超时处理问题或错误的兜底行为。
- 检查 `BootReceiver`、`HttpServer`、Manifest 改动以及 `UnsafeTrustManager` 的交互，确认没有引入启动回归或安全暴露。

## 期望输出格式

使用以下紧凑结构：

1. `问题`
2. `开放问题`（如有）
3. `剩余风险`（在没有发现问题，或验证受限时）
